## 2. 问题 A：付款单 `ACC-PAY-2026-00021` 存不住

### 2.1 现象

用户描述「无法保存」。实测：**草稿保存是成功的**（调用 `frappe.client.save` 返回正常，有 Version 记录）。真正发生的是：**保存/刷新之后，脚本把金额改回去了**，于是看起来像「存不住」。

### 2.2 业务口径（用户口述并确认）

- 发票 `ACC-SINV-2026-00064-1`：总额 = outstanding = **114,840 MZN**，`Wholesale Selling` 价目表，未收过款
- 现金付款：**3% 折扣 + 抹零**，其中抹零 = **直接抹去小数位（截断），不是四舍五入**（用户明确澄清）

```
114,840 × 97% = 111,394.80
抹零（截断）   = 111,394        ← 实收
抵扣 = 114,840 − 111,394 = 3,446.00   ← 3% 折扣 3,445.20 + 抹零 0.80
```

### 2.3 根因（两条叠加）

**① 算的是四舍五入到分，永远算不出「3% + 抹零」**

`solua_home/public/js/payment_entry_labels_v20261004.js`（改前）：

```js
function calculate_pronto_pagamento(gross, rate = CASH_DISCOUNT_RATE) {
    const total = Number(gross) || 0;
    const discount = Math.round(((total * rate) / 100) * 100) / 100;   // 折扣四舍五入到分
    return { discount, net: Math.round((total - discount) * 100) / 100 };
}
// 114,840 -> discount 3,445.20, net 111,394.80   ← 差 0.80，没有抹零
```

**② 脚本挂在 `refresh` 上，每次重算并覆盖用户手改的值**

```js
async function apply_pronto_pagamento(frm) {
    ...
    const gross = references.reduce((sum, row) => sum + flt(row.allocated_amount), 0);
    ...
    frm.doc.paid_amount = net;              // 直接赋值
    frm.doc.received_amount = net;
    frm.doc.total_allocated_amount = flt(gross, 2);
    frm.doc.deductions = (...).filter(row => row.account !== CASH_DISCOUNT_ACCOUNT);
    const deduction = frm.add_child("deductions");   // 删掉再重建抵扣行
    deduction.amount = discount;
}

frappe.ui.form.on("Payment Entry", {
    refresh(frm) {
        apply_payment_entry_labels(frm);
        apply_pronto_pagamento(frm);        // ← 每次打开/保存后都无条件重算
    },
    ...
});
```

触发条件：`custom_payment_term == "PRONTO PAGAMENTO"` 且 `mode_of_payment == "Cash"`。

**③ ERPNext 核心的硬约束（为什么差 0.80 就过不去）**

`erpnext/accounts/doctype/payment_entry/payment_entry.py`：

```python
def on_submit(self):                       # 约 203 行
    if self.difference_amount:
        frappe.throw(_("Difference Amount must be zero"))

def set_difference_amount(self):           # 约 1166 行
    # Receive 口径：difference = 总分配 + 未分配 − 实收 (+ 含税) − 抵扣合计
```

即：`实收 + 抵扣` 必须精确等于 `总分配`。折扣按「四舍五入到分」算时不抹零就留下 0.80 差额；而用户填了 111,394 后差额更大。

新算法（关键语义）：

```js
// 抹零：直接抹去小数位（向零截断），不做四舍五入
function truncate_decimals(value) {
    const cents = Math.round((Number(value) || 0) * 100) / 100;
    return cents < 0 ? Math.ceil(cents) : Math.floor(cents);
}
// 折扣 = 毛额 − 抹零后实收；抹掉的零头并入抵扣，保证 实收 + 抵扣 = 毛额 精确成立
function calculate_pronto_pagamento(gross, rate = CASH_DISCOUNT_RATE) {
    const total = Number(gross) || 0;
    const net = truncate_decimals((total * (100 - rate)) / 100);
    const discount = Math.round((total - net) * 100) / 100;
    return { discount, net };
}
```

设计要点：**折扣不是「3% 的四舍五入值」，而是毛额与实收的精确差额**。否则毛额带小数时（如 114,840.50）会出现 0.5 悬空、差额非 0 而被 ERPNext 拒绝。

## 3. 问题 B：静态资源被 Cloudflare / 浏览器长期缓存

### 3.1 现象

部署新脚本后，`https://erp.solua.one/assets/solua_home/js/payment_entry_labels_v20261004.js?v=cash-level3-20261004a`（**旧 URL**）仍然返回旧内容；另外，**已经开着的 desk 标签页**即使重新打开单据也仍在跑旧脚本（观察到的后果：它把客户端金额又改成了 111,394.80 / 3,445.20，DB 未受影响）。

### 3.2 实测证据

响应头（同一路径，不同 `?v=`）：

```
# 新 URL（本次部署的参数）
HTTP/1.1 200 OK
Server: cloudflare
Cache-Control: max-age=31536000
ETag: W/"6ac619f5-1988"
Age: 200
cf-cache-status: HIT

# 旧 URL
HTTP/1.1 200 OK
Cache-Control: max-age=31536000
ETag: W/"6ac1ee21-14e3"
Age: 273709          ← 约 3.2 天的边缘副本
cf-cache-status: HIT
```

源站 nginx（`/etc/nginx/conf.d/erp-ssl.conf`）：

```nginx
    location = /assets/solua_home/js/item_quick_entry.js {      # 第 20–24 行：既有先例
        try_files $uri =404;
        expires -1;
        add_header Cache-Control "no-store, no-cache, must-revalidate, proxy-revalidate, max-age=0" always;
    }

    location /assets {                                          # 第 26 行
        try_files $uri =404;
        add_header Cache-Control "max-age=31536000";            # 第 28 行：1 年，且不要求回源校验
    }
```

结论：**根因在源站的头**，Cloudflare 只是照着 `max-age=31536000` 缓存；而且它是**按含查询串的完整 URL** 缓存（所以我们改 `?v=` 能得到全新副本）。同时发现你们**早就为 `item_quick_entry.js` 单文件开过洞**——这就是这个环境既定的「必须随时更新」资产的写法。

### 3.3 为什么「purge Cloudflare」解决不了核心场景

真正会一直跑旧脚本的是**长期开着的 desk 标签页**。desk 是 SPA，它**不会再请求那个 js 文件** —— purge 之后它也不会请求。所以 purge 只能让「有人主动访问旧 URL」时拿到新内容（现实中几乎没人这样访问），对本问题帮助有限。

### 3.4 方案对比

| 方案 | 作用面 | 效果 | 代价 / 依赖 |
|---|---|---|---|
| **A. nginx 回源校验**（用户已选） | 源站头 | 以后每次请求都回源校验，浏览器/CF 都拿不到过期内容；`?v=` 变成双保险 | 需要 root 改 `/etc/nginx/conf.d/erp-ssl.conf` + reload |
| B. 应用层「版本监视器」 | desk 页面 | 常驻 JS 定期向一个绝不被缓存的接口查版本，变了就让页面自动重载 —— **能治长期开着的 SPA 标签页** | 新增功能与轮询；需要放某个「永远不会被缓存」的入口 |
| C. Cloudflare purge + Cache Rule | 边缘 | purge 清掉旧 URL 的边缘副本；Cache Rule 对 `/assets/solua_home/*` 改为 bypass | 需要 Cloudflare API Token 或面板权限（当前环境两者都没有） |
| D. 维持现状 | — | 新打开的页面一定拿到新脚本（`?v=` 机制是对的，手册 5.1 也这么规定） | 已有旧标签页需手动刷新一次 |

### 3.5 已准备的 A 方案（尚未执行）

脚本已放到服务器 `/tmp/fix-asset-cache.sh`（语法已校验），**需要 root 执行一次**：

```bash
ssh qq 'sudo bash /tmp/fix-asset-cache.sh'
```

脚本行为（幂等，重复执行会跳过）：

1. 备份 `erp-ssl.conf` → `erp-ssl.conf.bak-<时间戳>`
2. 在 `location /assets {` **之前**插入（nginx 中正则 location 优先于普通前缀 location，必然先命中）：

```nginx
    location ~ ^/assets/solua_home/(js|css)/ {
        try_files $uri =404;
        add_header Cache-Control "no-cache, must-revalidate, max-age=0" always;
    }
```

3. `nginx -t`（失败即停，不会 reload）
4. `systemctl reload nginx`
5. 用带随机参数的 URL 回读响应头

回滚：

```bash
cp -a /etc/nginx/conf.d/erp-ssl.conf.bak-<时间戳> /etc/nginx/conf.d/erp-ssl.conf
nginx -t && systemctl reload nginx
```

注意点：

- `item_quick_entry.js` 的 `location = …`（精确匹配）优先级更高，行为不变
- 这个 location 自带 `add_header`，服务器块上的 `X-Frame-Options` 等安全头**不会**被继承（对 js/css 无实质影响，与既有先例的取舍一致）
- 作用面是 js+css；要连图片一起回源校验，把正则里的 `(js|css)` 去掉
- **已开着的标签页仍需刷新一次**（SPA 不会再请求该文件）；要连这个也治，需要方案 B
